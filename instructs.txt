# 3. Fix Course-Lesson Relationship Consistency

This is a particularly important issue.

The project currently stores the course-lesson relationship in two places:

- `Lessons.CourseId`
- The `CoursesLessons` junction table.

Review all operations that create, update, delete, and read these relationships, including:

- `clsLessonsData.AddLesson`
- `clsLessonsData.UpdateLesson`
- `clsCoursesData.AssignLessonToCourse`
- `clsCourseLessonData.AddLessonToCourse`
- `clsCourseLessonData.DeleteLessonFromCourse`

- `SP_IssueCertificate`
- `clsProgress.EnsureEnrolledForLesson`

The problem is that some code paths update only `Lessons.CourseId`, while others update only `CoursesLessons`.

This can cause inconsistent results between course lesson listings, progress calculations, access authorization, and certificate issuance.

Required changes:

1. Trace the actual write and read paths throughout the project.
2. Determine the intended existing relationship behavior without changing the number of courses a lesson can belong to beyond what the current application supports.
3. Preserve the existing table structure.
4. Make all relationship updates consistent.
5. Execute related changes within a single transaction where necessary.
6. Prevent one representation of the relationship from being updated while the other remains inconsistent, whenever both represent the same relationship.
7. Handle lesson removal from a course and changes to its course association correctly.
8. Do not delete any table or column, and do not redesign the relationship.

Test that a lesson displayed inside a course is the same lesson included in progress calculations and certificate eligibility checks. Also ensure that adding, removing, or updating relationships never leaves inconsistent records.

# 5. Fix Payment and Order Issues in SQL

Do not change the payment provider or redesign the existing payment workflow. The objective is to secure the current flow with minimal changes.

## A. Prevent order modification after payment initiation

Review:

- `SP_CreateNewPayment`
- `SP_AddNewItemToOrder`
- `SP_RemoveItemFromOrder`
- Any other paths that add or remove `OrderItems`.
- `clsPayment.CreatePayment`

The problem: creating a payment saves the current amount, but the order remains `Pending`, and some order modification paths still allow its contents to change before the payment webhook arrives.

Required changes:

- When creating a payment, lock the corresponding order record inside an appropriate transaction.
- Prevent adding or removing order items while there is a `Pending` payment associated with the order.
- Use appropriate locking on the order record during payment creation and item modification to prevent race conditions.
- Allow modifications again after the payment reaches `Failed` or `Expired`, according to the existing workflow.
- Do not introduce a new order state or change the current state machine.
- Do not add new tables.
- Enforce this protection even when SQL procedures are called directly, not only through the BusinessLayer.

The amount actually paid must always match the products the user receives.

## B. Prevent multiple pending payments for the same order

Review `SP_CreateNewPayment` and `clsPayment.CreatePayment`.

Required changes:

- Prevent more than one `Pending` payment from existing for the same order.
- Preserve the current `IdempotencyKey` behavior.
- If the client submits the same key for the same order again, return the existing payment.
- If the same key is used with a different order, reject the operation.
- Ensure the protection works under concurrent requests, not merely through a preliminary C# check.
- Do not change the current Stripe session creation mechanism.

## C. Protect discount usage calculations

Review:

- `SP_CreateNewPayment`
- `clsDiscountCodesData`
- `clsCheckoutService`
- `clsDiscountCode`

Required changes:

- Verify that the discount exists when a `DiscountId` is supplied.
- Reject expired or invalid discounts.
- Validate that the discount rate is between 0 and 100 according to the existing rules.
- Protect the usage limit from being exceeded by concurrent payments.
- Ensure that duplicate webhook deliveries never increment discount usage more than once.
- Increment usage only according to the existing successful-payment workflow.
- Account for pending payments when checking limited usage, so concurrent operations cannot consume the final available use more than once.
- Do not change the meaning of `TotalUserNumber` or the current discount rules exposed by the API.

If a payment fails or is cancelled, it must not leave a permanent reservation that consumes an actual discount use.

## D. Fix discount expiration date handling

The `ExpireAt` column is of type `DATE`, but the application uses `DateTime` comparisons in SQL and C#.

Review:

- `SP_CreateNewPayment`
- `GetValidDiscountCodes`
- `clsDiscountCode.IsExpired`
- `clsDiscountCodesData`

Required changes:

- Make the expiration-date meaning consistent between C# and SQL.
- If the expiration date represents the last valid day, the discount must remain valid until the end of that day.
- Do not change the column type unless absolutely necessary.
- Use UTC consistently.

## E. Fix Stripe payment verification

Review:

- `StripeWebhookController`
- `clsStripeGateway`
- `PaymentsController`
- `clsCheckoutService`

The problem: the `checkout.session.completed` path does not verify `payment_status` before granting access.

Required changes:

- Never create enrollments or complete an order until Stripe confirms that `payment_status` is `paid`.
- Correctly handle `checkout.session.async_payment_succeeded`.
- Never grant products when `checkout.session.completed` arrives while `payment_status` is still `unpaid`.
- Preserve the existing webhook signature verification.
- Preserve idempotency and prevent duplicate webhook side effects.
- Never trust client-supplied data to declare a payment successful.

Also review these endpoints:

- `PUT /{id}/fail`
- `PUT /{id}/expire`

An ordinary user must not be able to change a payment's state without verification from the payment provider. Make these state changes dependent on a trusted webhook or an appropriately authorized administrative operation, while preserving the existing workflow and other system operations.
